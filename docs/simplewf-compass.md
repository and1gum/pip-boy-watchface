# SimpleWF: перевірка встановленого джерела компаса

Перевірено 2026-10-11 на SM-L715F через ADB. Встановлено
`com.simplewf.compass`, versionName `1.8`.

## Підтверджено аналізом встановленого APK

- Компонент: `com.simplewf.compass/.CompassComplicationService`.
- Типи manifest: `SHORT_TEXT,RANGED_VALUE,LONG_TEXT,SMALL_IMAGE`.
- `UPDATE_PERIOD_SECONDS=0`; привілейований дозвіл immediate updates не запитується.
- `generateComplicationData()` бере `CompassRepository.getCurrentHeading()`.
  Для `RANGED_VALUE` значення — азимут як float, мінімум 0, максимум 360.
  Текст містить напрямок і округлені градуси, наприклад формат `NE 42°`.
- OFF та очікування показуються текстом `OFF` і `...`; числове значення
  при відсутньому напрямку обмежується знизу нулем. Тому одного числа 0
  недостатньо для визнання даних валідними: треба перевіряти також TEXT.
- `CompassUpdateService` викликає публічний
  `ComplicationDataSourceUpdateRequester.requestUpdateAll()`.
- У колекторі закладено мінімальний інтервал між запитами 1000 мс при
  ввімкненому екрані, 5000 мс у static mode, 60000 мс при вимкненому екрані.
  Це інтервали запитів застосунку, а не виміряна частота рендерингу WFF.

## Висновок для нашого лімба

Формат придатний для власної геометрії: слот `RANGED_VALUE`, обертання групи
лімба на `-[COMPLICATION.RANGED_VALUE_VALUE]`. Бурштинові годинні позначки
мають залишитися поза групою обертання. Не потрібно використовувати готову
картинку SimpleWF чи повертати наш APK-провайдер.

Фізична перевірка оновлень у нашому циферблаті ще не виконана: у поточній
версії немає слота компаса. На момент перевірки dumpsys не показав активного
сервісу SimpleWF. Сам факт встановлення не означає, що realtime вже ввімкнено.
Також ще не виміряні затримка, поведінка AOD/пробудження та витрата батареї.

## Як реалізовано шлях оновлення

Додатково простежено DEX установленого APK, без копіювання його коду.

1. `CompassSensorManager` бере стандартні сенсори Android: акселерометр
   (тип 1), магнітне поле (тип 2), тиск (тип 6, для висоти). Події приходять
   через власний HandlerThread. Для напрямку використовуються
   `SensorManager.getRotationMatrix()` і `getOrientation()`, градуси
   нормалізуються до 0–360. Є згладжування векторів і кута, включно з переходом
   через 359/0. True North додає магнітне схилення з `GeomagneticField` за
   координатами; для магнітної півночі ця поправка не потрібна.
2. `CompassRepository` зберігає напрямок у StateFlow і веде лічильники клієнтів
   датчика за тегами. `getCurrentHeading()` повертає останнє значення.
3. Увімкнення realtime викликає `startService(CompassUpdateService)`.
   Сам сервіс повертає `START_STICKY`; у перевірених методах сервісу немає
   виклику `startForeground()`. Наявність дозволу FOREGROUND_SERVICE в manifest
   сама по собі не робить цей сервіс foreground. Не виявлено запиту WAKE_LOCK
   у manifest. Гарантованого безперервного фонового виконання це не доводить.
4. Колектор змін heading/location/altitude просить оновлення через
   `ComplicationDataSourceUpdateRequester.create(...).requestUpdateAll()`.
   Після цього система викликає `onComplicationRequest()`, який формує
   числовий payload із останнього напрямку. Тут немає immediate callbacks
   і не потрібен наш заблокований системний дозвіл.
5. Динамічний receiver обробляє SCREEN_ON, SCREEN_OFF, USER_PRESENT.
   При пробудженні додає клієнта ScreenActive й запитує оновлення відразу,
   додатково через 500 і 2000 мс. SCREEN_OFF знімає саме клієнта ScreenActive.
   Сервіс має власний тег клієнта, який видаляється в onDestroy; тому
   SCREEN_OFF не є доказом зупинки сенсорів. При активному realtime і
   збереженому сервісному клієнті repository залишає їх увімкненими.
6. Поточний азимут також синхронізується в локальне сховище приблизно раз
   на 10 секунд за наявності подій; це кеш, а не гарантія свіжості.

Це підтверджена структура програми, а не фізичний тест доставки 1 Гц у WFF.
Публічний API документований Google, але рекомендація для батареї — не
запитувати push-оновлення частіше ніж раз на 5 хвилин у середньому:
https://developer.android.com/training/wearables/complications/exposing-data#push-updates

## Уточнення попереднього дослідження

### Перемикачі SimpleWF 1.8

У `MainActivity.setupSettingsScreen()` кнопка `Optimization` прив'язана до
`setStaticModeEnabled()`, а не до системного дозволу Battery Optimization.
Static mode знижує частоту сенсорів з SENSOR_DELAY_UI до SENSOR_DELAY_NORMAL
і збільшує мінімальний інтервал push при ввімкненому екрані з 1 до 5 секунд.

`Always On Compass` змінює `always_on_enabled`; Activity використовує це
для FLAG_KEEP_SCREEN_ON (0x80). Це утримання екрана окремої програми компаса,
а не керування життєвим циклом ускладнення на циферблаті.

Окремо `checkBatteryOptimization()` перевіряє системне виключення з
оптимізації батареї та пропонує REQUEST_IGNORE_BATTERY_OPTIMIZATIONS.
Не слід плутати цей системний виняток з кнопкою `Optimization` усередині
SimpleWF. Жоден із двох внутрішніх перемикачів не доводить гарантованого
вимкнення сенсорів, коли наш циферблат перестає бути видимим.

Наш невдалий тест стосувався автоматичних immediate callbacks із системним
дозволом. Він не перевіряв публічні push-оновлення й не доводив, що живий
компас є ексклюзивом Samsung.

Витягнутий APK і повні діагностичні дампи залишені поза репозиторієм;
код стороннього застосунку в проєкт не копіюється.
